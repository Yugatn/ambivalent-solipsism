# Протокол резервного контекста

Резервный репозиторий сохраняет рабочее состояние экосистемы и решения, необходимые для восстановления следующего сеанса. Он не заменяет Git history.

## Вход

В начале каждого рабочего сеанса агент должен проверить доступность резервного репозитория, прочитать последний резервный файл, определить последнюю зафиксированную версию состояния, сравнить её с текущим состоянием основных репозиториев, определить незавершённые задачи и только после этого продолжать работу.

Если резервный репозиторий недоступен, нельзя молча считать контекст актуальным.

## Выход

Перед завершением сеанса агент должен дополнить резервный журнал. Записываются дата, репозитории, изменённые файлы, новые архитектурные решения, важные исправления, незавершённые задачи, известные проблемы, следующий рекомендуемый шаг и актуальные commit SHA, если они известны.

Запись добавляется в историю, а не заменяет предыдущую.

## Формат

### YYYY-MM-DD — Сеанс N

Состояние: краткое описание.

Изменено:
- репозиторий и файл.

Решения:
- принятое решение.

Проверено:
- ссылки;
- дизайн;
- тесты;
- канон.

Открыто:
- задача;
- вопрос;
- ошибка.

Следующий вход:
- что проверить первым.

## Защита

Резервный репозиторий должен быть максимально стабильным. Не изменять резервную историю ради сокрытия предыдущего состояния. Для критических состояний желательно иметь датированные снапшоты.

Резервный журнал не должен содержать секреты, токены, пароли или ненужные персональные данные.


## Карта связей в резервном состоянии

Резервная запись должна фиксировать не только изменения файлов, но и важные новые связи между ними.

Если в течение сеанса появилась новая архитектурная, концептуальная или проектная зависимость, записать её в разделе «Связи».

Формат:

Связь:
- источник;
- связанный узел;
- тип связи;
- почему она существует;
- что нужно проверить при следующем входе.

Резервный контекст таким образом сохраняет не только состояние файлов, но и состояние рабочей модели экосистемы.
