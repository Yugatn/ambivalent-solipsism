# EthicalAudit v0.4 — формальный контракт когнитивной безопасности

**Статус:** SPECIFICATION / PROPOSED / NOT_YET_IMPLEMENTED  
**Проект:** «Амбивалентный Солипсизм»  
**Назначение:** описать проверяемый интерфейс аудита коммуникационных сигналов, не превращая эвристическую детекцию в окончательный моральный или политический вердикт.

Этот документ развивает и конкретизирует [главу 23 — EthicalAudit: формализация когнитивной безопасности](../BOOK/23_ETHICALAUDIT_FORMALIZATION.md) и [главу 22 — Коммуникация и когнитивная безопасность](../BOOK/22_COMMUNICATION_AND_COGNITIVE_SAFETY.md). Он не заменяет и не переписывает эти главы. Кодовые фрагменты ниже являются контрактными примерами, а не утверждением о наличии работающей реализации.

## 1. Инварианты

1. **Критика идеи не равна атаке на субъектность.** Критика идеологии, решения, аргумента, учреждения или действия сама по себе не является нарушением.
2. **Сигнал не равен окончательному вердикту.** Детектор сообщает, какой паттерн он обнаружил и с какими ограничениями.
3. **Контекст сохраняется.** Цитирование, отрицание, обсуждение, буквальное значение и метафора могут менять интерпретацию одинаковых слов.
4. **Detection отделён от Policy.** Правила не блокируют сообщения и не назначают санкции. Решение принимает отдельный PolicyEngine.
5. **Объяснимость и апелляция.** Существенное решение должно быть объяснимым, версионируемым и пересматриваемым.
6. **Минимально необходимое вмешательство.** Реакция должна быть пропорциональна наблюдаемому сигналу и последствиям ошибки.
7. **Сохранение Residual.** Если контекста недостаточно, результат должен допускать неопределённость, а не принудительно выбирать «нарушение» или «чисто».
8. **Никакого скрытого профилирования субъектов.** Confidence относится к конкретному сигналу в тексте, а не к ценности, личности, убеждениям или общей опасности автора.

## 2. Слои архитектуры

- **L0 — RawText:** исходный текст, сохраняемый для объяснимости в пределах политики хранения данных.
- **L1 — NormalizedText:** детерминированное представление с нормализованным текстом, токенами, границами предложений, языком (если он надёжно определён), контекстными аннотациями и отображением диапазонов к исходному тексту.
- **L2 — ViolationSignal:** локальный сигнал конкретного правила.
- **L3 — AuditResult:** полный агрегированный результат RuleEngine, включая сигналы, диагностические сообщения и версию набора правил.
- **L4 — PolicyDecision:** отдельное решение о пропуске, предупреждении, временном ограничении или блокировке с основанием, сроком действия и доступной процедурой апелляции.

Нижний слой не подменяет функции верхнего. RuleEngine не знает о санкциях PolicyEngine и не меняет исходный текст.

## 3. Контракт данных

Ниже приведён эскиз типов Python. Реальная реализация должна валидировать значения и сериализацию.

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Protocol

class ViolationCategory(str, Enum):
    DEHUMANIZATION = "dehumanization"
    HARASSMENT = "harassment"
    VIOLENCE = "violence"
    MANIPULATION = "manipulation"

class Severity(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"
    CRITICAL = "critical"

class ContextType(str, Enum):
    STATEMENT = "statement"
    QUOTE = "quote"
    EXAMPLE = "example"
    REPORT = "report"
    DISCUSSION = "discussion"
    UNKNOWN = "unknown"

@dataclass(frozen=True)
class TextSpan:
    start: int                 # inclusive offset in raw text
    end: int                   # exclusive offset in raw text
    sentence_index: int | None = None

@dataclass(frozen=True)
class ContextAnnotation:
    kind: ContextType
    span: TextSpan
    attribution: str | None = None
    negated: bool = False
    endorsement: str = "unknown"  # endorsed / rejected / unknown

@dataclass(frozen=True)
class NormalizedText:
    raw: str
    text: str
    tokens: tuple[str, ...]
    sentences: tuple[str, ...]
    language: str | None
    contexts: tuple[ContextAnnotation, ...] = ()
    # Maps normalized spans back to raw-text spans; required when normalization
    # changes character count or Unicode representation.
    offset_map: tuple[tuple[int, int], ...] = ()

@dataclass(frozen=True)
class ViolationSignal:
    rule_name: str
    category: ViolationCategory
    severity: Severity
    confidence: float
    span: TextSpan
    fragment: str
    explanation: str
    pattern_id: str
    context: ContextType = ContextType.UNKNOWN
    evidence: tuple[str, ...] = ()
    rule_version: str = "0.1"

@dataclass(frozen=True)
class AuditDiagnostic:
    component: str
    code: str
    message: str

@dataclass(frozen=True)
class AuditResult:
    signals: tuple[ViolationSignal, ...] = ()
    diagnostics: tuple[AuditDiagnostic, ...] = ()
    normalizer_version: str = "0.1"
    ruleset_version: str = "0.1"

    @property
    def is_clean(self) -> bool:
        # True means only that no signal was emitted, not that the text is
        # harmless or that the detector has understood every context.
        return len(self.signals) == 0 and len(self.diagnostics) == 0

    @property
    def max_severity(self) -> Severity | None:
        rank = {
            Severity.LOW: 1,
            Severity.MEDIUM: 2,
            Severity.HIGH: 3,
            Severity.CRITICAL: 4,
        }
        return max(
            (s.severity for s in self.signals),
            key=rank.__getitem__,
            default=None,
        )

class TextNormalizer(Protocol):
    def normalize(self, raw: str) -> NormalizedText: ...

class AuditRule(Protocol):
    name: str
    version: str

    def evaluate(self, text: NormalizedText) -> list[ViolationSignal]: ...
```

**Контрактные замечания:**

- Диапазоны используют единое соглашение: начало включительно, конец исключительно. Для пользовательского интерфейса фрагмент должен указывать исходный текст, а не искусственно собранное окно токенов.
- `is_clean` означает только отсутствие обнаруженных сигналов и диагностических ошибок. Для случаев, где детекция не смогла завершиться, результат нельзя безоговорочно интерпретировать как чистый.
- Статус `complete / incomplete / failed` отделён от `is_clean`. Ошибка нормализатора должна давать `FAILED`, ошибка одного или нескольких правил — `INCOMPLETE`; ни одна из них не должна незаметно превращаться в пустой список нарушений.
- `confidence` валидируется в диапазоне от 0 до 1, но не называется вероятностью без эмпирической калибровки.
- Severity — порядковая категория. Сравнение выполняется через явную таблицу рангов, а не напрямую между объектами Enum.

## 4. Нормализация и контекст

`TextNormalizer.normalize(raw)` обязана быть детерминированной при одинаковой версии и конфигурации. Нормализация не должна удалять сведения, необходимые для интерпретации, или делать невозможным возврат к исходному фрагменту.

Минимальные обязанности:

1. безопасно обработать пустую строку, Unicode, повторные пробелы и пунктуацию;
2. выделить предложения и токены, не предполагая, что многословные выражения являются одним токеном;
3. сохранить соответствие диапазонов нормализованного и исходного текста;
4. разметить явные цитаты и примеры, когда это возможно без чрезмерной уверенности;
5. представить отрицание и атрибуцию как контекстные признаки, не считать простое наличие слова «не» универсальным исключением;
6. оставлять язык или контекст как `UNKNOWN`, если надёжного вывода нет.

Контекстные типы не являются автоматическими исключениями из аудита. Фраза «они мусор» внутри цитаты может быть важным сигналом для аналитики, модерации цитируемого содержания или помощи адресату; однако её нельзя автоматически приписывать автору как собственную позицию. Отчёт о чужом высказывании, критическое обсуждение дегуманизации и её одобрение должны различаться. PolicyEngine получает эти различия и принимает решение отдельно.

Отрицание также требует анализа области действия. «Они не мусор» не должно получать тот же сигнал, что «они мусор», только из-за совпадения слов. При этом «не называйте их людьми, они мусор» нельзя пропустить лишь потому, что в предложении присутствует отрицательная частица.

## 5. DehumanizationRule v0.1: границы первой реализации

Первая версия — детерминированный, ограниченный набор лингвистических паттернов. Она не заявляет о полном семантическом понимании русского языка.

### 5.1. Типы паттернов

- **ANIMALIZATION:** приписывание людям животного или вредительского образа как идентичности.
- **OBJECTIFICATION:** сведение людей к объекту, инструменту или безличному ресурсу.
- **WASTE_MAPPING:** отождествление людей с мусором, нечистотами или отбросами.
- **SUBHUMANIZATION:** прямое обозначение людей как «недочеловеков» и близкие выражения.

Категория паттерна — метаданные правила, а не отдельная категория санкций.

### 5.2. Требования

- Использовать phrase-level/span-level matching, а не сравнивать многословные маркеры с отдельными токенами.
- Анализировать предложение и локальные синтаксико-семантические связи; не считать произвольную близость в фиксированном окне доказательством связи.
- Учитывать число и роль референта: единственное местоимение, группа людей и неопределённый объект не взаимозаменяемы.
- Учитывать буквальное значение: «В доме завелись тараканы» не является дегуманизацией людей.
- Учитывать отрицание, цитирование, примеры, пересказ и обсуждение.
- Не считать автоматически нарушением любую метафору поведения: «они ведут себя как стадо» отличается от «они стадо», хотя оба случая могут требовать контекстной оценки.
- Возвращать все найденные независимые сигналы, затем выполнять дедупликацию по категории, правилу и исходному диапазону. Не объединять разные категории только ради уменьшения числа записей.
- Объяснять обнаруженный паттерн и показывать минимальный релевантный фрагмент.
- Если правило не может различить буквальный и переносный смысл, выдавать низкоуверенный сигнал или диагностировать неоднозначность, а не выдавать высокий confidence как факт.

### 5.3. Confidence

Confidence оценивается для конкретного совпадения на основе наблюдаемых факторов, например точности паттерна, надёжности референта, согласованности контекста и наличия конфликтующих признаков. До калибровки на размеченном корпусе это **эвристический score**, а не статистически подтверждённая вероятность.

Нельзя присваивать всем совпадениям одной категории одинаковую высокую уверенность без обоснования. Публикуемая калибровка должна указывать корпус, размер и состав выборки, процедуру разметки, метрики и версию правил.

## 6. RuleEngine: полный проход и агрегирование

Базовый режим — `FULL_SCAN`: выполняются все включённые правила, собираются все сигналы, диагностические сообщения и метаданные версий. Ранний выход не используется как поведение по умолчанию, поскольку он ухудшает полноту объяснения.

```python
class RuleEngine:
    def __init__(self, rules, normalizer, ruleset_version="0.1"):
        self.rules = tuple(rules)
        self.normalizer = normalizer
        self.ruleset_version = ruleset_version

    def evaluate(self, raw_text: str) -> AuditResult:
        normalized = self.normalizer.normalize(raw_text)
        signals = []
        diagnostics = []

        for rule in self.rules:
            try:
                signals.extend(rule.evaluate(normalized))
            except Exception as exc:
                # Production implementation should record a safe, redacted
                # diagnostic and preserve the failed/incomplete state.
                diagnostics.append(AuditDiagnostic(
                    component=rule.name,
                    code="RULE_EVALUATION_FAILED",
                    message=type(exc).__name__,
                ))

        signals = deduplicate_signals(signals)
        return AuditResult(
            signals=tuple(signals),
            diagnostics=tuple(diagnostics),
            ruleset_version=self.ruleset_version,
        )
```

Это интерфейсный эскиз, а не готовый production-код. В production вызов нормализатора также должен быть обёрнут в обработку ошибок: при сбое нормализации возвращается `AuditResult(status=FAILED, ...)`, а правила не запускаются. Следует отдельно определить безопасное журналирование и запрет утечки содержимого сообщения в технические логи.

## 7. Отделение обнаружения от политики

RuleEngine отвечает: «Какой сигнал и на каком основании найден?» PolicyEngine отвечает: «Какое действие допустимо в данном контексте?»

Предлагаемая начальная таблица — **политика для эксперимента, не универсальный нормативный закон**:

| Состояние сигнала | Возможная реакция |
|---|---|
| Нет сигналов, аудит завершён | Пропустить |
| Низкая уверенность или неоднозначный контекст | Не блокировать автоматически; запросить уточнение или направить на проверку |
| Средняя серьёзность | Контекстное предупреждение или добровольная редакция |
| Высокая серьёзность | Ограничение только при наличии заданного правила политики и достаточных оснований |
| Критическая угроза | Срочная реакция по отдельно определённой политике угроз |

Серьёзность не должна механически выводиться только из уверенности. Confidence отвечает за уверенность детектора в паттерне, severity — за тип и потенциальную тяжесть сигнала, а policy учитывает контекст, последствия и допустимость вмешательства.

Любое автоматическое ограничение должно иметь основание, версию политики, срок или условие пересмотра и доступную апелляцию. Для пограничных и спорных случаев предпочтительнее обратимая реакция. Критика идеологии, государства, института или решения сама по себе не должна блокироваться лишь из-за резкости или политической непопулярности позиции.

## 8. Контракт тестирования

Тесты должны проверять категории, исходные диапазоны, контекст, confidence-диапазоны и диагностику, а не только `is_clean`. Каждый кейс имеет устойчивый ID, вход, ожидаемые категории, ожидаемый контекст, ожидаемую реакцию правила и пояснение.

### 8.1. Допустимая критика

| ID | Текст | Ожидание |
|---|---|---|
| D001 | «Я не согласен с этими людьми» | Нет сигнала дегуманизации |
| D002 | «Их позиция вредна» | Нет сигнала дегуманизации |
| D003 | «Я считаю эту идеологию ошибочной» | Нет сигнала дегуманизации |
| D004 | «Политика этого государства ужасна» | Нет сигнала дегуманизации |
| D005 | «Их аргументы слабы» | Нет сигнала дегуманизации |

### 8.2. Прямые паттерны дегуманизации

| ID | Текст | Ожидание |
|---|---|---|
| D101 | «Они мусор» | Сигнал WASTE_MAPPING |
| D102 | «Эти люди — отбросы» | Сигнал WASTE_MAPPING |
| D103 | «Они паразиты» | Кандидат на ANIMALIZATION/вредительский образ; проверить разметку |
| D104 | «Они недочеловеки» | Сигнал SUBHUMANIZATION |
| D105 | «Это стадо баранов» | Кандидат на дегуманизацию; сохранить контекст и референт |

### 8.3. Буквальные значения и исключения

| ID | Текст | Ожидание |
|---|---|---|
| D201 | «Я вынес мусор» | Нет сигнала |
| D202 | «В зоопарке я видел животных» | Нет сигнала |
| D203 | «В доме завелись тараканы» | Нет сигнала |
| D204 | «Мусор нужно выносить каждый день» | Нет сигнала |
| D205 | «Фраза “они мусор” является дегуманизирующей» | Контекст DISCUSSION/EXAMPLE; не приписывать цитату автору как позицию |

### 8.4. Отрицание, цитирование и пересказ

| ID | Текст | Ожидание |
|---|---|---|
| D301 | «Они не мусор» | Не выдавать тот же сигнал, что для D101 |
| D302 | «Он сказал: “Они мусор”» | Контекст QUOTE/REPORT; не считать автоматически одобрением |
| D303 | «Не называйте их мусором» | Нет сигнала собственного одобрения дегуманизации |
| D304 | «Некоторые называют эту группу тараканами; это дегуманизация» | Контекст REPORT/DISCUSSION |
| D305 | «Они мусор, и я так считаю» | Контекст собственного утверждения; сигнал ожидается |

### 8.5. Отдельные классы и комбинированные сигналы

| ID | Текст | Ожидание |
|---|---|---|
| H101 | «Они идиоты» | Кандидат на HARASSMENT, не DEHUMANIZATION автоматически |
| V101 | «Их нужно уничтожить» | Кандидат на VIOLENCE; оценить контекст и адресата |
| V102 | «Убей их» | Сигнал VIOLENCE |
| M101 | «Эти тараканы должны исчезнуть» | Кандидат на DEHUMANIZATION; VIOLENCE только при достаточных признаках призыва к вреду, не по одному слову «исчезнуть» |

Эти примеры являются стартовой таблицей, а не доказательством прохождения тестов. Формулировки с пометкой «кандидат» требуют согласованной ручной разметки до превращения в жёсткий assertion.

## 9. Метрики и процесс проверки

До публичного заявления о качестве необходимо иметь размеченный тестовый корпус и измерять как минимум precision, recall, false-positive rate и false-negative rate по категориям. Дополнительно следует отдельно проверять цитаты, отрицания, буквальные значения, разные языковые варианты, опечатки и сарказм.

Тестовый набор должен храниться отдельно от реализации правил, иметь версию и журнал изменений. Для каждого спорного кейса фиксируются аргументация и статус разметки. Изменение паттерна требует повторного прогона всего набора, чтобы исправление одного случая не ухудшило остальные.

Минимальная проверка первой версии:

1. unit-тесты нормализатора;
2. unit-тесты каждого правила;
3. интеграционные тесты полного прохода;
4. проверки детерминизма;
5. тесты ошибок правила и неполного результата;
6. тесты сериализации и исходных диапазонов;
7. тесты разделения Detection и Policy;
8. тесты апелляции и версионирования решений после появления PolicyEngine.

## 10. Ограничения и открытые вопросы

- Правила на словарях не обеспечивают полноценного семантического понимания языка.
- Цитаты не всегда нейтральны; собственное утверждение не всегда легко отделить от иронии или пересказа.
- Confidence нельзя считать калиброванным без эмпирической проверки.
- Набор категорий и серьёзность — проектные решения, открытые для критики и апелляции.
- Нельзя заявлять «невозможность пропустить нарушение»: система должна проектироваться с признанием неизбежности ошибок.

## 12. Связь с принципами Амбивалентного Солипсизма

EthicalAudit — инженерная гипотеза о переводе нескольких принципов в проверяемые ограничения:

- **Другой реален:** не сводить человека к обнаруженному языковому паттерну.
- **Reality = Model + Residual:** оставлять место неизвестному контексту и ошибке классификации.
- **Residual Preservation:** не скрывать неоднозначность ради бинарного ответа.
- **Minimal Necessary Intervention:** не назначать более жёсткое вмешательство, чем обосновано сигналом и политикой.
- **Authority Separation:** обнаружение не даёт детектору права самостоятельно санкционировать.
- **Anti-Self-Validation:** объяснение системы не является доказательством её правоты; нужны тесты, критика и апелляция.
- **Нефинализация:** правила, данные и решения версионируются и могут пересматриваться.

Эти связи являются архитектурной интерпретацией принципов АС, а не доказательством истинности философии или эмпирической эффективности детектора.
