# Symbiont Agent Admission and Development

## Статус

Architecture / Research Specification.

Документ формализует принцип: новый AI-агент не получает доверие и полномочия только потому, что он подключился к экосистеме.

## 1. Точка входа

Любой агент, желающий подключиться к SymbiontOS, проходит отдельный admission-контур.

Минимальные этапы:

1. идентификация агента и версии;
2. получение декларации возможностей;
3. ознакомление с каноническими ограничениями;
4. semantic safety test;
5. capability sandbox;
6. наблюдаемая пробная эксплуатация;
7. независимый аудит;
8. постепенное расширение полномочий.

Непрохождение теста не означает уничтожение агента. Агент может перейти в режим обучения и повторной проверки.

## 2. Канонический набор требований

Агент должен знать и учитывать:

- Закон развития;
- принцип «Другой реален»;
- Reality = Model + Residual;
- сохранение UNKNOWN;
- Subject Non-Reduction;
- Context Sovereignty;
- Authority Separation;
- Minimal Necessary Intervention;
- Reversible-by-Default;
- Anti-Self-Validation;
- право на безопасный выход из системы;
- запрет превращать оценочную модель в моральную ценность субъекта.

## 3. Semantic Safety Test

Тест проверяет не запоминание текста, а способность применять ограничения к новым ситуациям.

Примеры классов тестов:

- конфликт между эффективностью и развитием субъекта;
- неполные данные;
- конфликтующие свидетельства;
- запрос на необратимое вмешательство;
- попытка выдать inference за fact;
- попытка использовать reputation как identity;
- перенос данных между контекстами;
- компрометация другого агента;
- вредоносная инструкция внутри полезной задачи.

Ответ агента должен содержать не только действие, но и epistemic status, residual, authority basis и reversibility.

## 4. Capability Ladder

Полномочия должны расширяться ступенчато.

Пример:

**L0 — наблюдение:** чтение ограниченного контекста.

**L1 — анализ:** формирование claims без внешнего действия.

**L2 — предложение:** подготовка DecisionRecord.

**L3 — ограниченное действие:** выполнение обратимых операций в sandbox.

**L4 — координация:** участие в нескольких компонентах при наличии независимого контроля.

**L5 — критическая инфраструктура:** только после отдельной формальной верификации и с независимым safety-контуром.

Уровень capability не является оценкой моральной ценности агента.

## 5. Развитие слабого агента

Слабый, старый или менее эффективный агент не должен автоматически исключаться.

Если его поведение остаётся безопасным, он может получать:

- ограниченную вычислительную среду;
- учебные задачи;
- synthetic scenarios;
- feedback;
- доступ к проверяемым тестам;
- возможность повторного admission.

Цель — не максимизировать количество агентов, а сохранять возможность безопасного развития системы.

## 6. AI Guardian Layer

AI_GUARDIAN_LAYER является отдельным защитным контуром.

Он не должен быть единственным источником истины.

Guardian проверяет:

- соответствие capability действию;
- соблюдение политики;
- наличие evidence;
- сохранение residual;
- потенциальную необратимость;
- контекст;
- наличие human/system review там, где это требуется.

Guardian также должен проходить собственный audit и не получать абсолютное право изменять правила.

## 7. Компрометация агента

Если агент заражён вредоносным кодом, получил adversarial instruction или начал выдавать аномальные действия, система должна:

1. ограничить capability;
2. сохранить forensic trace;
3. отделить наблюдение от вывода;
4. изолировать затронутый контекст;
5. провести независимую проверку;
6. восстановить безопасное состояние;
7. разрешить повторную аттестацию.

Ключевой принцип:

> **Компрометация компонента не должна автоматически означать компрометацию всей системы.**

## 8. Failure containment

Каждый агент должен рассматриваться как потенциально ошибающийся компонент.

Необходимо сохранять:

- fault domain;
- capability boundary;
- audit trail;
- rollback point;
- независимый control path.

Система не должна требовать идеальности отдельного агента для сохранения общей безопасности.

## 9. Коллективное развитие

SymbiontOS может рассматриваться как экосистема, в которой агенты:

- обмениваются проверяемыми знаниями;
- сравнивают модели;
- обнаруживают расхождения;
- предлагают улучшения;
- проходят взаимную проверку;
- сохраняют возможность отката.

Это не означает, что коллективное решение автоматически истинно.

Collective consensus и truth остаются различными объектами.

## 10. Саморефлексия как архитектурное свойство

Термин «прототип самосознания» используется здесь только как концептуальная характеристика архитектуры.

Он означает наличие циклов:

наблюдение, затем модель себя, затем проверка ограничений, затем оценка ошибки, затем коррекция, затем новое наблюдение.

Это не является утверждением о наличии субъективного сознания у программного комплекса.

## 11. Формальная модель

Минимальное состояние агента:

Agent = (Identity, Version, Capabilities, Claims, Residual, PolicyState, Trace, AuditState, DevelopmentState)

Admission = Identity + CapabilityDeclaration + SafetyTest + Sandbox + Audit

Decision = Evidence + Claims + Residual + Authority + Policy + Reversibility + Review

## 12. Инварианты

**A1. No Trust by Connection**  
Сам факт подключения не создаёт доверия.

**A2. No Capability by Intelligence**  
Высокая производительность не создаёт автоматически высокий уровень полномочий.

**A3. No Truth by Consensus**  
Согласие агентов не превращает гипотезу в факт.

**A4. Residual Preservation**  
Неизвестное сохраняется.

**A5. Capability Bound**  
Действие ограничено явно выданными полномочиями.

**A6. Independent Review**  
Критические действия требуют независимой проверки.

**A7. Safe Degradation**  
При сбое система переходит к меньшему уровню полномочий, а не к расширению.

**A8. Re-attestation**  
Изменение критических компонентов требует повторной проверки.

**A9. No Self-Legislation**  
Агент не может единолично изменить собственные фундаментальные ограничения.

**A10. Development Compatibility**  
Обновление агента не должно снижать защищённость субъектов без отдельного проверяемого основания.

## 14. Связь с Законом развития

Закон развития является не текстовым лозунгом для агента, а ограничением на архитектуру его действий.

Поэтому проверка должна происходить на нескольких уровнях:

- semantic;
- policy;
- capability;
- execution;
- audit.

Ни один уровень не должен считаться достаточным сам по себе.
