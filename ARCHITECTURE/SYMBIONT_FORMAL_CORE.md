# Symbiont Formal Core

## Статус

**Architecture / Research Specification**

Этот документ добавляет формальный архитектурный слой к концепции «Амбивалентного Солипсизма». Он не заменяет существующие философские, конституционные и технические положения проекта, а связывает их общей моделью ограниченного вмешательства при неполной наблюдаемости.

## 1. Назначение

Symbiont рассматривается как формальная вычислительная архитектура, в которой выполнение, наблюдение, реконструкция, интерпретация, принятие решений и вмешательство разделены по полномочиям.

Основная проблема архитектуры:

> Система должна действовать, не предполагая, что её модель полностью совпадает с реальностью.

Отсюда следует принцип:

> **Модель необходима для действия, но модель не получает автоматически права становиться реальностью, субъектом, законом или приговором.**

## 2. Четыре фундаментальных объекта

В минимальной модели различаются:

- **Fact** — наблюдаемое событие или иной зафиксированный факт;
- **Model** — реконструкция состояния на основании доступных фактов;
- **Residual** — неизвестное, ненаблюдаемое, противоречивое или недостаточно определённое;
- **Action** — изменение состояния системы или внешней среды.

Общий цикл:

**Fact, затем Model и Residual, затем Decision, затем Action, затем новый Fact.**

Ни один из этих объектов не должен автоматически отождествляться с другим.

## 3. Reality = Model + Residual

Принцип AS получает формальную реализацию:

`Reality = Model + Residual`

Для вычислительной системы это означает, что результат реконструкции должен включать не только восстановленное состояние, но и границу неизвестного:

`DEFT(EventGraph) = (StateVector, Residual)`

Residual может содержать:

- неизвестные события;
- отсутствующий контекст;
- ненаблюдаемое состояние;
- конфликтующие свидетельства;
- неопределённость идентичности;
- ограничения самой модели.

Неизвестное является валидным состоянием системы и не обязано быть искусственно преобразовано в «истину» или «ложь».

## 4. Epistemic Type System

Система должна различать эпистемический статус утверждений.

Базовые статусы:

- **OBSERVED** — непосредственно наблюдаемое;
- **RECONSTRUCTED** — детерминированно восстановленное из истории;
- **INFERRED** — полученное выводом;
- **ASSUMED** — принятое как предположение;
- **UNKNOWN** — недостаточно данных;
- **CONFLICTING** — имеются несовместимые свидетельства.

Концептуально допустимы типы:

`Observed<Event>`

`Reconstructed<State>`

`Inferred<Intent>`

`Unknown<Context>`

`Conflicting<Claim>`

Это препятствует незаметному превращению вывода модели в факт.

## 5. Claim Model

Утверждение является отдельным объектом:

`Claim = (subject, predicate, value, evidence, epistemic_status, confidence, timestamp)`

Confidence относится к конкретному утверждению и не означает вероятность истинности всей модели.

Например, система может одновременно хранить:

- высокую уверенность в идентичности;
- среднюю уверенность в текущем состоянии;
- неизвестное намерение;
- предполагаемый риск.

Один глобальный показатель уверенности не заменяет эту структуру.

## 6. Authority Separation

Каждый слой обладает только необходимой ему формой власти.

| Слой | Основная функция | Полномочие |
|---|---|---|
| Hardware | физическое исполнение | исполнение инструкций |
| Kernel | изоляция и ресурсы | execution authority |
| Event Fabric | наблюдение и причинность | observation authority |
| DEFT | реконструкция | reconstruction authority |
| CTO | формирование задач | task-generation authority |
| PICCS | защищённый транспорт и контекст | transport authority |
| EthicalAudit | семантическая оценка | annotation authority |
| Consensus | согласование | agreement authority |
| Reputation | измерение истории | measurement authority |
| Economic layer | стимулы | incentive authority |
| Agent | локальное действие | capability-bounded authority |

Основной принцип:

> **Оценка не создаёт полномочия.**

R, Viability, Risk, Reputation и другие производные показатели не получают автоматически права управлять kernel, consensus или identity.

## 7. Subject Non-Reduction

Производная модель субъекта не является самим субъектом.

`R != Subject`

`Profile != Subject`

`Prediction != Subject`

`StateVector != Subject`

`RiskScore != Subject`

Модель может описывать отдельный аспект субъекта, но не исчерпывает его.

Это техническое продолжение принципа:

> **Другой реален.**

## 8. Identity, State, Reputation и Residual

Эти четыре пространства должны быть разделены.

**Identity** отвечает на вопрос «кто это».

**State** отвечает на вопрос «в каком состоянии находится субъект сейчас».

**Reputation** описывает выводы о наблюдаемой истории.

**Residual** показывает, что система не знает.

Поэтому изменение Reputation не должно автоматически изменять Identity.

## 9. Cell Principle

В Symbiont процесс или агент моделируется как:

`Cell_i = (Identity_i, State_i, Policy_i, Capabilities_i, Trace_i, Residual_i, Viability_i)`

Cell является вычислительной абстракцией субъекта, а не буквальной биологической клеткой.

Viability:

`V_i(t) in [0,1]`

является производным показателем устойчивости функционирования.

Viability не означает моральную ценность субъекта.

`Viability != Value`

Аналогично:

`R != Moral Worth`

## 10. DNA как набор инвариантов

«DNA» SymbiontOS является метафорой набора формальных ограничений:

- kernel invariants;
- Event Fabric invariants;
- causal consistency;
- capability rules;
- transition constraints.

DNA не является runtime state.

Биологическая аналогия не должна непосредственно управлять control logic.

## 11. Event Fabric

Event Fabric является append-only causal evidence layer.

Минимальное событие:

`Event = (id, type, sender, receiver, timestamp, payload_hash, causal_context, epoch)`

Causal context может содержать vector clock и parent event IDs.

Event Fabric может хранить не только события, но и:

- Claims;
- Decisions;
- Interventions;
- Reviews;
- revisions.

Изменение интерпретации не должно стирать старую запись. Вместо этого создаётся новая версия утверждения.

## 12. Reconstruction

Системное состояние может быть представлено как детерминированная редукция истории:

`SystemState(t) = Reduce(EventLog <= t)`

Для DEFT:

`DEFT(EventGraph) = (StateVector, Residual)`

Одинаковая история должна приводить к одинаковой реконструкции при одинаковой версии reducer.

## 13. DecisionRecord

Значимое решение должно быть явным объектом:

`Decision = (subject, evidence, claims, residual, authority, policy_basis, intervention_level, reversibility, expiration, review)`

Decision не является скрытым побочным эффектом классификатора.

Значимое решение должно быть реконструируемым по истории.

## 14. Intervention Contract

Вмешательство должно иметь контракт:

`InterventionContract = (target, reason, evidence, authority, scope, duration, reversibility, review_condition)`

Это позволяет различать наблюдение, аннотацию, уведомление, временное ограничение, отзыв capability и другие уровни вмешательства.

## 15. Minimal Necessary Intervention

При сопоставимой эффективности система должна рассматривать вариант с меньшей областью вмешательства.

Интенсивность вмешательства является самостоятельным параметром.

Не следует превращать результат классификатора непосредственно в максимально сильное действие.

## 16. Reversible-by-Default

При высокой неопределённости и наличии альтернатив система должна отдавать приоритет обратимым действиям.

Чем выше неопределённость и потенциальная необратимость действия, тем выше требования к обоснованию.

Этот принцип не означает запрет на сильные действия. Он означает необходимость отдельного основания для необратимого вмешательства.

## 17. Anti-Self-Validation

Система не должна считать собственное вмешательство независимым подтверждением гипотезы, которая послужила основанием этого вмешательства.

Например, изменение поведения после ограничения не доказывает само по себе первоначальную гипотезу.

Собственное действие является частью причинной истории и должно учитываться как возможный confounder.

## 18. Counterfactual Separation

Наблюдаемое после вмешательства не следует автоматически считать траекторией, которая произошла бы без вмешательства.

Поэтому система должна различать:

- observed trajectory;
- intervention-affected trajectory;
- counterfactual estimate.

Это особенно важно для адаптивных систем и оценки причинных эффектов.

## 19. Graceful Epistemic Failure

Если система не может определить состояние с достаточным основанием, она должна иметь возможность корректно перейти в:

**UNKNOWN**

а не быть вынуждена выбрать TRUE или FALSE.

Неопределённость является допустимым состоянием, а не исключением.

## 20. Context Sovereignty

Контекст является отдельным объектом:

`Context = (context_id, participants, purpose, epoch, visibility, retention)`

Данные, допустимые в одном контексте, не становятся автоматически допустимыми в другом.

Перенос данных между контекстами требует отдельного основания.

Это особенно важно для PICCS и Eugene Messenger.

## 21. Reputation и R

R является производной характеристикой наблюдаемой траектории:

`R_i(t) = g(EventTrace_i(t))`

R может использоваться для:

- анализа;
- стимулов;
- исследования;
- статистики;
- формирования рекомендаций.

R не должен напрямую определять:

- consensus quorum;
- proposer selection;
- kernel scheduling;
- identity;
- моральную ценность;
- право субъекта на существование.

## 22. Symbiont Consensus

Consensus должен быть отделён от reputation и incentives.

Архитектурная последовательность:

**Observed Contribution, затем Verified Contribution, затем Proof-of-Development, затем Reward, затем Reputation.**

Consensus safety не должна зависеть от R.

Это сохраняет различие между:

- agreement;
- incentive;
- reputation.

## 23. Symbiont Coin

Proof-of-Development может учитывать подтверждённую полезную активность, relay, участие в инфраструктуре и другие верифицируемые действия.

Но:

`Reward != Identity`

`Reward != Consensus Authority`

`Reward != Moral Value`

Экономический слой не должен становиться скрытым механизмом управления безопасностью consensus.

## 24. Failure Taxonomy

Архитектура различает:

- **F1 Observation Failure** — событие не наблюдалось;
- **F2 Reconstruction Failure** — состояние восстановлено неправильно;
- **F3 Epistemic Failure** — inference принят за fact;
- **F4 Causal Failure** — корреляция принята за причинность;
- **F5 Authority Failure** — компонент действовал вне полномочий;
- **F6 Intervention Failure** — действие оказалось чрезмерным или необратимым;
- **F7 Audit Failure** — решение невозможно реконструировать;
- **F8 Context Failure** — данные использованы вне допустимого контекста.

Такой классификатор должен использоваться при Threat Modeling.

## 25. Базовые инварианты Symbiont

**S1 Kernel Isolation**  
Kernel не зависит от semantic logic user space.

**S2 Event Immutability**  
Записанное событие не изменяется.

**S3 Event Structure**  
Каждое событие имеет корректную структуру.

**S4 No Policy in Kernel**  
Policy layer не управляет kernel control flow.

**S5 Log Completeness**  
Наблюдаемые значимые действия имеют event trace.

**S6 Causal Consistency**  
Причинные зависимости сохраняются.

**S7 Reconstruction Determinism**  
Одинаковая история даёт одинаковую реконструкцию.

**S8 Non-interference**  
Cognitive Runtime не вмешивается непосредственно в Ring 0.

**S9 Non-biological Control**  
Биологическая метафора не определяет control logic.

**S10 Authority Separation**  
Компонент не получает полномочия только потому, что он что-либо классифицирует.

**S11 Interpretation Non-Identity**  
Интерпретация не является identity или субъектом.

**S12 Residual Preservation**  
Неизвестное не преобразуется автоматически в определённое.

**S13 Anti-Self-Validation**  
Собственное вмешательство не считается независимым подтверждением собственной гипотезы.

**S14 Graceful Epistemic Failure**  
UNKNOWN является валидным состоянием.

**S15 Subject Non-Reduction**  
Ни одна производная модель не является полным эквивалентом субъекта.

**S16 Context Sovereignty**  
Перенос данных между контекстами требует отдельного основания.

## 26. Архитектурные кольца

Рекомендуемая реализация:

**Ring 0: seL4 или другой детерминированный execution substrate**

Kernel, capabilities, scheduling, memory isolation, IPC.

**Ring 1: Event Fabric / Symbiont Mediator**

Наблюдение, causal graph, event stream, evidence storage.

**Ring 2: Cognitive Runtime**

DEFT, CTO, PICCS, EthicalAudit и другие semantic services.

**Ring 3: Agents and Applications**

Пользовательские процессы, агенты, Eugene Messenger и прикладные системы.

Для Linux Event Fabric может получать данные через eBPF, tracepoints, ftrace, perf, LSM и другие наблюдательные механизмы.

## 27. Общий цикл Symbiont

**Execution, затем Observation, затем Reconstruction, затем Interpretation, затем Decision, затем Bounded Intervention, затем новый Event.**

Каждый переход имеет собственную область полномочий.

Главный принцип:

> **Observation does not imply Control.**

И:

> **Interpretation does not imply Authority.**

## 28. Связь с Амбивалентным Солипсизмом

Архитектура является техническим продолжением следующих принципов AS:

- **Другой реален**: субъект не сводится к собственной модели наблюдателя;
- **Reality = Model + Residual**: любая реконструкция сохраняет остаток неизвестного;
- **Cognitive Sovereignty**: интерпретация не должна автоматически уничтожать автономию;
- **Law of Development**: вмешательство должно учитывать здоровье, развитие, будущие возможности и обратимость;
- **право на выход**: системы должны иметь механизмы безопасного прекращения участия;
- **сложность не является ошибкой**: сложная система должна сохранять различия между субъектами, контекстами и уровнями знания.

## 29. Формальный следующий этап

Следующая стадия формализации:

`SymbiontKernel.tla`

`EventFabric.tla`

`CellModel.tla`

`Authority.tla`

`Residual.tla`

`DecisionRecord.tla`

`Context.tla`

`SymbiontConsensus.tla`

В дальнейшем эти модели должны проверяться композиционно.

Probabilistic claims, такие как ожидаемое изменение Viability, не следует выдавать за обычные детерминированные TLC invariants. Для них необходим отдельный вероятностный или статистический слой.

## 30. Итог

Symbiont не требует идеального AI.

Он предполагает возможность:

- неполного наблюдения;
- ошибки реконструкции;
- ошибочной интерпретации;
- неизвестности;
- конфликта свидетельств;
- ошибки причинного вывода.

Задача архитектуры состоит в том, чтобы эти ошибки не получали автоматически больше власти, чем им положено.

> **Модель может ошибаться. Система должна быть устроена так, чтобы ошибка модели не становилась автоматически необратимой властью над реальностью.**
